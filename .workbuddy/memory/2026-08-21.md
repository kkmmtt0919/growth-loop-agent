## 技术选型决策（用户确认）

- **起点主线**：数据持久化层（用户选定，理由=不依赖外部阻塞+是所有P0地基+越晚做技术债越大）。
- **数据库选型**：PostgreSQL（关系型+事务，满足账本幂等和多用户隔离；不选 SQLite/MongoDB）。
- **托管方案**：分两阶段——MVP 验证用 **Supabase**（自带 Auth + Row Level Security 直接解决多用户隔离硬需求，免费档够用，微信登录需自接 OAuth 回调），国内正式上线前迁**腾讯云 PostgreSQL**（国内访问+合规）；PG→PG 迁移成本可控。
- **部署联动**：国内上线意味着 Next.js 也要放国内云（Vercel 国内访问差不可用），这是和数据库绑定的整体决策。
- **改版 Next.js 约束**：AGENTS.md 硬要求——写任何代码前必须读 node_modules/next/dist/docs/ 确认 16.3 的数据库集成方式和 API 变化。
- **动手前**：先读 Next.js 16.3 数据库文档 + 看清 demo-data 完整形状 → 设计 schema → 用户确认 → 实现。

## 设计审核转向（用户审查意见，重大）

用户审核后指出：①"PG 迁移不难"不能理解成"无痛迁移"——Supabase ≠ 纯 PG，业务不能绑定 Supabase 特有 API；②MVP 第一阶段不做微信登录，先跑通"邮箱/密码注册→保存→重登→数据还在"闭环，再接微信 OAuth。

**已写的 supabase-js 版数据层（lib/db/*、匿名登录、RLS、apply_ledger RPC）作废重写**，新方向：
- 分层：Next.js API → lib/service（业务）→ lib/repo（pg + 参数化 SQL）→ PostgreSQL；Supabase 只当托管 PG（连接串），腾讯云迁移=换 DATABASE_URL。
- 鉴权：自建邮箱/密码（bcrypt）+ JWT（jose）；新增 /api/auth/register|login|me；前端登录 UI。
- schema：纯标准 PG DDL（去 auth.users 外键/RLS/auth.uid() 依赖/RPC），保留 6 表+索引+updated_at 触发器；幂等入账改 Repo 事务 ON CONFLICT。
- 依赖变化：加 pg、bcryptjs、jose；移除 @supabase/supabase-js。
- 隔离：Service 层 WHERE user_id（RLS 降级为可选，不依赖）。
